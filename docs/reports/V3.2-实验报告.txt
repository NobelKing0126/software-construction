三、状态流转与职责

ReserveStatus 保持 PENDING、PASS、REJECT、CANCEL 四种枚举值。
ReserveRecordService.requireTransition 集中维护以下规则：
PENDING -> PASS：管理员审核通过。
PENDING -> REJECT：管理员审核驳回。
PENDING -> CANCEL：学生本人取消未审核预约。
PASS -> CANCEL：学生本人取消已通过预约。
其余12种组合均不合法，包括保持原状态的重复操作和回到 PENDING。审核/取消入口先验证权限和记录存在，再调用同一流转校验。没有通用状态框架，也没有自行增加预约开始后禁止取消的时间规则。

新增 InvalidReserveStatusException，覆盖非法状态变更及不可取消；新增 ResourceOccupiedException，覆盖预约时间冲突与资源不可用；无权审核、越权取消继续复用 PermissionDeniedException，空驳回原因复用 ParameterEmptyException。异常均继承 BusinessException，由原 UI 异常处理转换为 Result.fail 中文提示。Result<T> 的 success/msg/data 格式与行为没有变化。
通过时自动记录 LocalDateTime.now()，资源变为 OCCUPIED；驳回时要求非空白原因，原样保存原因并记录审核时间，不修改资源。取消不清空已有原因或审核时间。取消一条 PASS 后，只有该资源不存在其他 PASS 才恢复 AVAILABLE。资源有其他 PASS 时，即使驳回另一条申请也不会释放资源。
保留原冲突条件 start < 已有end 且 已有start < end：时间有重叠才冲突，端点恰好相接可以审核通过。资源占用时学生不能新提交申请；已存在的相接 PENDING 申请可以在无时间冲突时继续审核。PASS 删除保护和修改资源状态的保护原样保留。
管理员新增编号13“查看全部待审核预约”，仅筛选 PENDING；原菜单编号不变。学生查询显示状态、rejectReason 和 auditTime。记录列表与条件筛选使用 Stream；FileReserveRecordDao.findById 使用 stream().filter().findFirst().orElse(null)，Service 使用 Optional.ofNullable(...).orElseThrow(...) 将缺失记录转为原中文业务提示。
UI 负责输入展示，Service 负责业务和保存失败补偿，DAO 负责访问及持久化调用；三个 Service 之间没有新增依赖。

四、字段持久化与旧数据兼容

ReserveRecord 新增 String rejectReason，默认空字符串；新增 LocalDateTime auditTime，默认 null。保留原八参数构造方法及现有字段接口。展示时空审核时间显示“未记录”，不虚构旧记录审核时间。
reserve.txt 新格式顺序为：
recordId|resourceId|applicantUsername|applyTime|reserveStartTime|reserveEndTime|status|remark|rejectReason|auditTime
仍以 UTF-8 保存。原因沿用原有竖线、反斜杠、回车、换行转义；时间沿用 LocalDateTime 的 ISO 文本，空审核时间保存为空字段。user.txt、resource.txt 格式和原转义函数完全不变。
加载只接受8或10字段；旧8字段记录的新增字段取默认空值，同一文件允许新旧记录并存。只查询旧文件不会重写，下一次正常保存统一写成10字段。损坏字段数、无效时间/状态、重复ID和无效转义仍按原逻辑加载失败，不自动修复。
双文件联动仍按原顺序先保存预约、再保存资源。保存前保留旧状态、旧原因、旧审核时间和资源状态；IOException 后同时恢复内存，若预约已写入则补偿写回旧值。旧八字段文件在补偿写回时会升级为十字段，因此恢复的是原业务值，不声称旧文件字节完全相同。该差异在控制台场景14单独核验。二次补偿也失败时继续提示“数据保存失败且预约状态恢复失败，请检查 reserve.txt 和 resource.txt。”，不隐藏磁盘与内存可能不一致的问题。
