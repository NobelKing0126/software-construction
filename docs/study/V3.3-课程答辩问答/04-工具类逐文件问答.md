# 工具类逐文件问答

本章覆盖 `src/utils` 的两个 Java 文件，依据当前 V3.3 Service 抽象补充版本。以下推演和测试建议用于理解代码，除明确引用已有实验报告外，不表示本轮已经执行这些测试。

## src/utils/FileUtil.java

[查看源码](../../../src/utils/FileUtil.java)。职责是将实体集合与 UTF-8 文本记录相互转换，包含用户、资源、预约三组加载/保存函数，以及 `parseReserveRecord`、`writeRecord`、`escape`、`splitRecord` 等私有细节。调用者主要是三个 File DAO。

### T01. 为什么 FileUtil 是 final 类、私有构造器、静态方法？这是不是单例？

`FileUtil` 不需要为每个调用者保存不同的实例状态，所以通过类名直接使用加载和保存函数。私有构造器阻止外部正常创建无用途的实例，`final` 表示不通过继承扩展这个类。文件名和分隔符是类级常量。

这不是本项目 Service/DAO 的单例结构：它没有 `INSTANCE`，也没有返回某个工具对象的 `getInstance()`，而是根本不要求调用者持有实例。把所有静态工具类都叫单例会混淆“无需对象的操作”和“控制对象数量”。如果以后需要不同文件路径或替代存储，优先在 DAO 边界设计，不必为了模式名称给这个工具类增加对象。

### T02. 为什么文件名只是 user.txt 等相对路径？IDE 中更改工作目录会发生什么？

`new File("user.txt")` 使用相对路径，它通常相对于 Java 进程的工作目录解析，不是自动相对于 `FileUtil.java` 的位置。当前从项目目录启动就访问项目目录的数据；测试把工作目录切到独立场景后，会访问该场景的数据文件。

这是配置与运行环境的一部分。两个运行配置即使使用同一套 class 文件，也可能因工作目录不同看到不同的数据。单例只在每个进程中共享那次加载出的集合，不会把不同工作目录的数据自动合并。答辩演示若出现“之前注册的账号消失”，应先核对工作目录，再判断是否是保存逻辑问题。

### T03. BufferedReader、InputStreamReader、FileInputStream 为什么套三层？UTF-8 起什么作用？

`FileInputStream` 从文件取得字节，`InputStreamReader` 按 UTF-8 将字节解码成字符，`BufferedReader` 再提供缓冲和 `readLine()`。写入方向相反：`BufferedWriter` 组织字符，`OutputStreamWriter` 编码成 UTF-8，`FileOutputStream` 输出字节。这种组合使每个对象承担不同职责，体现组合复用。

统一指定 UTF-8 可以减少不同机器默认字符集造成的中文乱码，但源文件编译编码、控制台编码和数据文件编码是三个不同环节。仅设置 IDE 终端编码不能替代读写时的字符集约定。缓冲主要减少频繁底层调用，并不把文件写入变成事务。

### T04. try-with-resources 为什么比手工 close 更合适？抛异常时还能关闭吗？

读写函数在 `try (...)` 中声明 reader 或 writer，离开作用域时会自动关闭资源，包括循环或解析中途抛异常的情况。关闭最外层包装流会连带关闭底层流，避免文件句柄泄露。手工关闭容易遗漏异常分支，或在多个返回点中重复代码。

需要进一步说明：关闭过程本身也可能失败。正文先抛异常、关闭又抛异常时，Java 会保留正文异常，并将关闭异常作为受抑制异常记录；自动关闭不等于“永不抛错”。当前 `throws IOException` 因而仍有必要。[Oracle try-with-resources 说明](https://docs.oracle.com/javase/tutorial/essential/exceptions/tryResourceClose.html)。

### T05. loadUsers 和 loadResources 是怎样把一行变成对象的？它们验证了所有业务规则吗？

两者先确保文件存在，再逐行读取并调用 `splitRecord`。用户记录要求 4 个字段，然后解析注册时间；资源记录要求 6 个字段，再构造 `CampusResource`。最后把对象收集为列表交给 DAO。

这主要是表示格式的检查，不等于完整业务校验。资源加载不会调用 Service 判断名称、状态或角色规则，用户加载也没有统一查重逻辑。文件中字段数量正确但状态拼写错误，可能仍被资源加载接受。课程上应区分“语法或格式合法”“领域数据合法”“当前操作者有权限”：三者处在不同职责边界，不能因为成功读成对象就认为数据完全可信。

### T06. parseReserveRecord 为什么同时检查字段数、空 ID 和重复 ID？短路求值有什么作用？

预约记录接受 8 或 10 个字段，并要求 ID 非空、同一次加载过程中未出现重复 ID。`HashSet<String> ids` 的 `add` 在新元素加入时返回 true，已存在时返回 false，因此 `!ids.add(id)` 同时完成记录和查重。集合在一次 `loadReserves` 中创建，避免不同加载调用无意共用查重状态。

条件中的 `||` 从左到右短路：字段数不符合要求时，不再执行后续 ID 检查。这里 `splitRecord` 本身也总会加入最后一个字段，但先检查整体形状再读取指定字段，仍使解析逻辑更清楚。预约加载的查重要求不能推断成用户和资源加载也做了相同检查；后两者当前没有这一段逻辑。

### T07. 为什么预约文件兼容 8 字段和 10 字段？这属于什么设计问题？

旧记录只有预约基本字段，新版本增加驳回原因和审核时间。解析函数先构造基本预约对象，只有 10 字段记录才读取新增字段；8 字段记录保留空原因和空审核时间，不把当前时间伪装成历史审核时间。这是持久化格式演化中的向后兼容：新程序能读取旧数据。

保存函数统一写出 10 字段，所以旧数据经新程序保存后会采用新格式。不能据此声称旧程序也能读取新数据，那是另一方向的兼容性。若以后字段持续增加，可以设计显式格式版本和迁移规则；当前只支持两种已知长度，是符合小型课程项目规模的最小方案。

### T08. 为什么不能直接使用 line.split("\\|") 分割记录？

字段本身可以包含竖线，例如预约备注 `讨论|实验`。如果直接按所有竖线切开，会把同一个字段误当成两个字段。默认 `String.split` 还涉及尾部空字段处理，容易影响空备注、空驳回原因等记录。当前协议使用反斜杠标记转义，分隔符是否起分隔作用取决于前面的解析状态。

`escape` 将原始反斜杠、竖线、回车和换行分别编码；`splitRecord` 按同一协议恢复。关键是写入和读取必须形成配对约定，不能写入只转义竖线、读取却把所有反斜杠都当转义符。此处循环比简单正则更容易明确状态和非法输入的处理。

### T09. splitRecord 如何体现有限状态机思想？为什么最后还要添加一次字段？

它用 `escaped` 表示两个状态。普通状态遇到反斜杠进入“等待转义字符”状态；遇到分隔符就提交当前字段并清空缓冲；其他字符直接追加。转义状态只接受 `r`、`n`、竖线和反斜杠，恢复相应字符后回到普通状态。无法识别的转义或行尾未完成的转义会抛 `IOException`。

循环遇到的是“字段之间”的分隔符，最后一个字段后面未必有分隔符，所以循环结束必须再添加一次。即使最后一个字段为空也要保留，例如末尾分隔符后还有一个空字段。这是协议完整性，不是多余操作。可用状态表说明，而不必只背诵每条 if：

| 状态 | 输入 | 动作 |
| --- | --- | --- |
| 普通 | 反斜杠 | 等待转义字符 |
| 普通 | 未转义分隔符 | 提交字段、清空缓冲 |
| 普通 | 其他字符 | 追加字符 |
| 转义 | 支持的转义字符 | 解码、回到普通状态 |
| 转义 | 不支持的字符或结束 | 拒绝该记录 |

### T10. 为什么 writeRecord 使用 String... fields？这与抽象有什么关系？

三种记录的字段数量不同，但写入时都需要“依次转义字段、字段间写分隔符、末尾换行”。可变参数让调用方按各实体自己的字段顺序传入，公共函数只处理共同的文本序列化步骤。这样把变化部分留在三个 `save*` 中，把稳定部分集中在一个函数中。

`String...` 在方法内部作为数组使用，并不是任意类型的动态参数。调用者仍负责字段顺序和必需字段非空；`writeRecord` 不知道哪个位置是用户名、状态或时间。这里的提取有三个实际调用点，能够减少协议写法不一致的风险，不是为了“每行都必须封装”为单次代码增加抽象。

### T11. 保存预约时为什么将某些 null 转为空字符串？能否推断所有字段都允许 null？

`saveReserves` 对备注、驳回原因和审核时间作专门处理：这些字段在合法流程中可能尚不存在，文本协议用空字段表示它们。审核时间不为空时才调用 `toString()`，避免对合法缺失值解引用。

其他字段如预约 ID、起止时间和状态按当前模型被当作必需数据直接使用。`escape(null)` 会因访问长度而失败，`null` 时间调用 `toString()` 也会失败。当前实体的无参构造器和 setter 并未彻底保证这些要求，因此正常业务构造路径之外仍可能产生非法对象。准确说法是“对几个已知可选字段作了显式约定”，不是“保存函数处理了所有空值”。

### T12. saveUsers、saveResources、saveReserves 为什么是全量覆盖？失败时有什么风险？

每个保存函数遍历当前内存集合，使用未开启追加模式的 `FileOutputStream` 重写对应文件。课程项目数据量小，这种方式容易理解，删除和修改记录也不用原地定位文本行。代价是一次小修改也可能写整个文件，读写成本随集合增大而上升。[FileOutputStream 的构造与追加模式说明](https://docs.oracle.com/javase/8/docs/api/java/io/FileOutputStream.html)。

更重要的是原文件可能在写入过程中已被截断或部分覆盖，后续异常不保证磁盘仍是旧内容。将实体字段改回去只恢复内存，不自动恢复已经写坏的文件。临时文件写好再替换可以改善单文件更新，但还需考虑替换能力、失败处理和持久化要求；同时更新两个文件的原子性仍需要另外设计。

### T13. 为什么 parseReserveRecord 把 RuntimeException 包装成 IOException，而 loadUsers 没有同样处理？

预约时间解析、枚举转换等可能抛运行时异常，当前预约解析把它们包装为带 cause 的 `IOException`，使调用者把这些问题理解为“预约文件格式不可读取”。保留 cause 有利于调试时看到真正失败点。

用户注册时间解析则可能直接抛运行时异常，没有在 `loadUsers` 中做同样的包装；这属于现有错误转换策略不完全一致。启动装配层会把 DAO 初始化失败转换成对应中文提示，但这不能说明底层异常类型已经统一。未来若整理错误契约，可统一文件解析边界的异常表达，同时保持原提示和失败行为；本资料不把这种建议说成已经实现。

### T14. 怎样测试转义和兼容解析，比只测试“保存后文件存在”更有说服力？

先定义性质：对协议允许的字段列表，写入再读取应恢复相同字段内容和顺序。测试输入应含普通中文、空字段、末尾空字段、竖线、反斜杠、真实换行以及“反斜杠后跟字母 n”这两种不同内容。后者不能与真实换行混淆，因为原反斜杠本身也会被转义。

再测试拒绝行为：未知转义、末尾单独反斜杠、错误字段数量、重复预约 ID、非法日期和非法预约状态。兼容性需分别准备 8 字段旧记录和 10 字段新记录，并检查旧记录不会凭空得到审核时间。可通过公开 `save*`/`load*` 在临时目录做往返验证，无需为了测试把私有解析函数改为 public。以上是测试设计，不能未经运行就声称全部通过。

## src/utils/Result.java

[查看源码](../../../src/utils/Result.java)。这是带成功标志、消息和数据的泛型结果对象。关键函数包括两个构造器、三个 `success` 重载、`fail`、字段访问器和 `toString`。它是各 Service 和控制台共享的返回约定，不负责执行业务规则。

### T15. 为什么使用 Result<T>，而不是 Object、字符串或为每种业务单独写结果类？

`Result<User>` 明确登录成功可能携带用户，`Result<List<CampusResource>>` 明确资源查询返回列表。编译器可以检查调用端使用的数据类型，减少“先取 Object 再强制转换”的错误。与单个字符串相比，它把可供程序判断的成功标志、供人阅读的消息和业务数据分开。

这是参数化抽象：稳定结构是 success/msg/data，变化的是 T。泛型主要在编译阶段提供类型约束，不能理解为运行时为每个 T 自动生成全新 Result 类。[Oracle 泛型类型擦除说明](https://docs.oracle.com/javase/tutorial/java/generics/erasure.html)。它也不能证明数据在业务上合法，例如 `Result<User>` 里的 User 仍可能被调用者修改。

### T16. 静态方法上的 <T> 与类名 Result<T> 中的 T 有什么关系？

类的类型参数描述一个 Result 实例的数据类型。静态方法属于类本身，不依附于某个已经选定 T 的实例，所以 `public static <T> Result<T> success(T data)` 声明的是方法自己的类型参数，恰好也叫 T。编译器可根据实参和使用位置推断这个方法类型。

因此 `Result.success(user)` 可以得到 `Result<User>`，而不需要先创建一个 Result 对象再调用。不能把它解释为“所有静态调用共用一个 T”或“静态方法读取了某个对象的泛型参数”。这是泛型方法与泛型类结合的常见写法，能在保留类型信息的同时简化创建调用。

### T17. 为什么使用 success/fail 创建结果，私有三参数构造器有什么价值？

命名创建方法在调用处表达意图：`Result.fail("用户不存在")` 比 `new Result(false, "用户不存在", null)` 更容易读懂，也减少反复传布尔值和 null。它们最终调用私有三参数构造器，集中约束失败结果的数据必须为空。

这些是静态工厂方法，但不能仅因“工厂”二字就说使用了 GoF 工厂方法模式。当前也保留了 public 无参构造器和 setter，所以外部并非只能通过命名方法创建结果。设计优点是方便和统一表达，局限是对象仍可被分步修改；若需要不可变结果，必须进一步调整整个构造与修改约定，而不只是把构造器名称改一下。

### T18. Result.success("文本") 到底把文本当消息，还是当数据？重载有什么陷阱？

当前同时有 `success(T data)` 和 `success(String msg)`。当直接传入字符串时，Java 会选择更具体的 String 参数重载，所以它被当作消息，`data` 为 null。这里的 `<T>` 并不能取消重载解析规则。

如果希望成功结果携带字符串数据，应明确使用两个参数，例如 `Result.success("操作成功。", "文本数据")`。这是接口可用性上的真实取舍：重载让常用成功消息调用简短，但数据类型恰好也是 String 时不够直观。解释函数设计原因时既要说出便利，也要能展示这个反例；不能声称三个重载在任何情况下都毫无歧义。

### T19. 为什么失败时 data 一定被清空？哪些方法共同维护这个不变式？

私有三参数构造器使用 `success ? data : null`，`setSuccess(false)` 清空现有数据，`setData` 也只在 success 为 true 时接受数据。这使通过正常 public API 构造和修改后的失败结果不携带旧成功数据，降低 UI 误展示历史结果的风险。无参构造后的默认状态是 false、null、null，也满足这个有限约束。

注意逻辑方向：失败意味着数据为空，不代表成功就必须有数据。删除成功只需要消息，`Result<Void>` 的数据自然可为空。`setSuccess(true)` 也不会恢复先前被清掉的数据。回答不变式问题时要准确写成单向蕴含，不能把它误读为双向条件。

### T20. 有了静态工厂为什么还保留无参构造和 setter？这样的对象不可变吗？

当前代码允许先创建空结果，再设置 success、msg、data，这属于普通可变 Java 对象的使用方式。它保留了灵活性，但读者必须考虑设置顺序：在默认失败状态下直接 `setData(user)` 会被丢弃，之后再 `setSuccess(true)` 不会自动找回 user。

不能凭空断言无参构造是某个框架要求的，因为当前项目没有显示使用这样的框架。可据源码说明它提供了分步构造途径，并指出业务代码通常采用命名静态方法更清楚。是否删除这些入口是另一次 API 设计决策，应先检查调用方和课程要求，而不是在讲解时假装当前 Result 已经不可变。

### T21. Result<Void>、Result<?> 与 Result<Object> 有什么不同？

`Result<Void>` 表示本次操作不提供实际负载，如删除资源；方法本身仍返回 Result，不能把 Void 等同于方法返回类型 void。`Result<?>` 表示数据类型未知，但调用者可以读取成功标志、消息，并把数据作为 Object 检查，适合统一展示不同结果。`Result<Object>` 则是明确以 Object 为类型实参的一种 Result。

泛型通常不协变，`Result<User>` 不能简单赋值给 `Result<Object>`，但可以赋值给 `Result<?>`。因此 ConsoleOutput 使用通配符能接收不同业务结果。通配符并不会保留 `List<ReserveRecord>` 的全部运行时类型信息，控制台仍需要按实际展示需求处理对象和列表。

### T22. Result.toString 与异常处理有什么关系？为什么调试输出也要关注封装？

`toString` 把 success、msg、data 组合成字符串；当 data 非空时，会间接使用该对象的字符串表示。本轮 User 的 `toString()` 已移除密码，因此包含 User 的结果也不会再经此路径输出密码。这个变化来自 User 的显示封装，Result 本身没有新增字段过滤机制，其他数据对象仍需自行控制其字符串表示。

Result 也不负责捕获异常。Service 在返回 Result 之前若抛出 BusinessException 或 IOException，正常返回路径就被中断；由 UI 的 catch 决定如何展示。设计时应区分“正常返回的数据结构”“错误控制流”“面向用户的展示文本”和“调试日志”，不能把一个通用 `toString()` 当成所有场景的输出协议。

## 本章可以现场手推的两个例子

```java
// 例一：重载选择。以下是教学示例，不是新增生产代码。
Result<String> first = Result.success("只有提示");
Result<String> second = Result.success("操作成功。", "真正的数据");
// first 的 msg 为“只有提示”，data 为 null；second 的 data 为“真正的数据”。

// 例二：可变结果的设置顺序。
Result<String> third = new Result<String>();
third.setData("先设置的数据");
third.setSuccess(true);
// data 仍为 null，因为 setData 时 success 尚为 false。
```

理解这两个例子后，可以继续追问：“如果 API 让调用者频繁记住隐含顺序，应该增加文档，还是改变接口？”合适答案需要结合现有调用规模、兼容性和误用成本，而不是一律增加更多重载或 setter。
