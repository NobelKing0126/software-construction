# 工程文件与历史版本问答

Java 源码的 35 个文件已在 01—04 逐一讲解。本附录补充配置、数据、历史报告和模型文件的课程问题。Git 内部对象、生成的 class 文件和旧版演示产物不作为新的业务源码逐个解释；它们的作用与使用边界在下文说明。未读取根目录既有账号数据来编造演示，也未将 Word 文件内容当作新的课程规格。

## 配置与项目管理文件

### P01. AGENTS.md 为什么也是工程的一部分？它能代替需求说明或接口契约吗？

该文件规定工作目录、版本保存、实验报告和最小实现等协作要求。它帮助多人或辅助工具采用一致工作方式，减少覆盖未提交文件、混合版本和虚构运行记录的问题。课程上可将其理解为过程约定的一种载体。

它不定义预约冲突公式、账号校验等全部业务规则，也不等同于 Java 编译器能检查的接口。工程中的过程规则、业务需求、设计模型与可执行代码作用不同，需要相互一致。当前还引用个人环境中的 RTK 约定，说明有些工具习惯属于开发环境，不是业务系统运行所必需的依赖。

### P02. .gitignore 为什么忽略 *.class、out/、target/ 和 .idea/？

源代码和配置是可维护输入，class 和构建目录一般是可以由编译重新生成的输出。将生成物提交容易出现源码已改而 class 仍旧、不同机器构建互相覆盖等问题。IDE 私有配置也常混有本地路径或个人设置，不一定适合共享。

忽略规则并不等于删除文件，也不自动停止跟踪已经提交过的文件。当前根目录仍可能存在未跟踪数据或报告，这与是否忽略构建产物是两回事。答辩时应能解释仓库保存什么，以及如何从保存的输入重建程序，而不是只展示本机恰好能运行的一份旧 class。

### P03. .vscode/settings.json 中的 JavaSE-1.8 与 UTF-8 设置各管什么？

当前配置的运行时名称为 `JavaSE-1.8`，路径指向本机 Temurin 8，另设置调试参数 `-Dfile.encoding=UTF-8`。前者表达编辑器中的 Java 环境选择，后者影响该调试启动的默认字符编码。源码中 FileUtil 又显式指定了 UTF-8，这是不同层面的设置。

配置文件表达意图，不是某次编译实际使用该 JDK 的运行证据。命令行 PATH、外部终端或其他 IDE 可能选择不同 Java。课程报告应该记录实际执行的 javac/java 路径和版本输出；若只修改配置但没有运行，不能写成已用该版本完成验证。

### P04. 校园资源预约系统.iml 记录了什么？为什么 src 要标记为源码目录？

当前模块文件把 `src` 标为非测试源码目录，并继承项目 JDK。IDE 由此理解哪些目录中的 Java 文件需要编译、包路径怎样对应以及使用哪个项目环境；它不是运行时业务对象，也不是 Maven 的依赖清单。

“继承项目 JDK”意味着仅查看 `.iml` 还不足以知道实际版本，必须继续查看项目配置或运行配置。命令行使用 javac 直接编译源文件时，并不因为该文件存在就自动读取其中所有 IDE 设置。能区分 IDE 模型与 Java 语言规则，有助于解释“换个编辑器为什么也能运行”。

### P05. .idea/misc.xml 为什么值得检查？当前它与 JDK 8 实验报告是否完全一致？

本次读取到 `languageLevel="JDK_17"`、`project-jdk-name="17"`，编译输出目录为 `out`。这是 IDEA 当前项目配置，和 VS Code 指向 Temurin 8 的设置并不一致。该事实不能改写已有报告中使用绝对路径执行 JDK 8 的真实记录，也不能证明当前 IDEA 每次启动都使用 JDK 8。

答辩应明确：“代码上次用 Temurin 8 实际编译和回归；本机 IDEA 项目配置另指向 17，需要在演示环境中核对。”本轮只解释现状，没有修改用户 IDE 配置。若后续统一环境，应单独验证 IDEA 项目 SDK、语言级别和实际运行配置，不只修改文档里的版本文字。

### P06. .idea/modules.xml 与 .idea/vcs.xml 分别有什么作用？

`modules.xml` 当前将项目关联到 `校园资源预约系统.iml`；`vcs.xml` 将项目目录关联到 Git。这些信息帮助 IDE 组织模块和显示版本状态，但不会实现注册、预约或持久化。

两文件可分别追问：“模块关系丢失会影响什么？”以及“IDE 能显示 Git 状态是否等于已经提交？”前者可能影响编辑器识别源码，后者答案是否定的：工作区修改、暂存和提交是不同状态。实际提交记录应通过 Git 查询确认，不能根据文件颜色或一个保存按钮推断。

### P07. .idea/.gitignore 与 .idea/workspace.xml 为什么体现共享配置和个人状态的区别？

当前 `.idea/.gitignore` 列出 workspace、shelf、HTTP 请求、本地数据源等忽略项；根 `.gitignore` 又整体忽略 `.idea/`。`workspace.xml` 属于 IDE 本地工作状态，不是业务数据文件或 Java 编译输入。

可以分别问：“忽略规则为什么可能有两层？”和“所有 IDE 文件都应提交吗？”回答应依据协作需要选择共享内容，避免把个人路径、临时任务或运行状态当成所有人必须使用的设计。本附录没有逐项解释 workspace 内部随编辑器变化的状态，也不将其作为系统功能需求。

## 数据和运行产物

### P08. user.txt 与 resource.txt 为什么不能当作源代码？怎样解释它们的格式？

它们是程序运行数据，内容会随着注册或资源管理改变。根据当前 FileUtil，用户记录依次为用户名、密码、角色、注册时间，资源记录依次为 ID、名称、类型、状态、位置、描述；字段采用约定的分隔与转义规则。这里说明的是代码定义的格式，没有展示用户现有文件中的真实内容。

可分别追问：“注册后只修改内存但不写 user.txt，重启会怎样？”以及“resource.txt 的状态拼错但字段数量正确，加载是否一定拒绝？”前者会丢失未保存变化，后者当前加载不做完整状态业务校验。这说明持久化格式、领域约束和业务操作是不同问题。

### P09. 当前根目录没有列出 reserve.txt，是否说明预约功能没有实现？

不能仅凭某一工作目录是否已有该文件判断功能。当前 FileUtil 的预约加载逻辑会在文件缺失时创建空文件，而测试曾在隔离目录运行，文件未必出现在项目根目录。应查看程序代码、启动工作目录、实际测试输入和输出。

预约文件新格式包含 10 个字段，加载兼容旧 8 字段格式。缺文件、空文件、损坏文件是三个不同场景：分别涉及创建初始数据、合法空集合和启动拒绝。课程验证中应区分它们，而不是都解释为“没有预约记录”。

### P10. .v22-isolated-demo/ 下的数据文件和 classes/ 为什么不能证明当前版本运行正确？

该目录保留旧版演示数据与编译产物。运行其中的 class 文件，执行的是那些字节码所对应的版本，不会因为当前 `src` 已修改就自动升级。其数据与根目录数据也不会自动互相同步。

对其中的 `user.txt`、`resource.txt` 可问“这是哪个场景的数据、由哪版程序生成”；对 `classes/` 可问“它由哪组源码和哪个编译器产生”。如果不能回答来源，就不能把演示结果作为当前版本的证据。保留旧产物可以用于对照，但必须标明版本和工作目录，不能混用。

### P11. 根目录实验报告.docx 与 docs/reports/ 中的版本报告应怎样建立关系？

Word 文件可以是提交课程作业的排版载体，按版本命名的文本报告则便于与代码和 Git 差异一起审阅。文件名本身不足以证明内容对应最新代码，本轮没有读取并审定该 Word 文件的正文，所以不对其中的数字和截图作事实背书。

答辩前应检查它标记的版本、截图来源、实际 JDK、提交号和文本报告是否一致。截图能说明某次界面状态，不能替代所有异常分支的验证；文本中写“运行成功”也必须有对应输入和输出。无论载体是什么，都应维护证据与版本的对应关系。

## 计划、历史报告与设计模型

### P12. docs/plans/V1.0-项目初始化.md 为什么当时要求把业务写在 main 中？今天看起来不是坏设计吗？

该阶段计划明确要求暂不分层，将固定账号、输入与凭据判断集中在入口中，以先建立可运行基线并保留课程阶段特征。评价一个版本应结合当时的目标，而不是把后来阶段的全部架构要求倒推回初始化作业。

随着注册、文件、资源和预约功能增加，职责混杂的代价才逐渐显现，后续重构展示了结构演化。这个过程可以用来回答“为什么不一开始就使用所有模式”：设计复杂度应由当前需求支撑，同时为已经出现的变化整理边界，避免为了未来想象提前堆叠框架。

### P14. V3.1-三层架构.puml 中为什么仍把 Service 画为普通类并使用构造器注入？

因为它标记的是 V3.1，而当前 Service 接口和单例实现属于后续演化。该图源中写明了当时通过构造器注入 DAO 的结构，不能当作当前版本的完整类图，也不应直接覆盖以抹去历史。

适合追问：“模型与源码不一致一定意味着模型错误吗？”需要先比较版本。历史模型在对应版本下可能正确；若用于讲解当前版本，就应新增或更新带明确版本标识的模型。当前补充报告与本学习资料已提供反映新接口关系的图示。

### P15. V3.1-三层架构.svg 与 V3.1-三层架构.png 有什么区别？

SVG 是矢量图表达，适合缩放和查看文本、连线；PNG 是像素图，通常便于粘贴到报告。两者都主要服务于阅读与展示，不是业务源码。对 SVG 可以问“放大为什么仍能保持清楚”，对 PNG 可以问“为什么放大后可能模糊”。

模型真实性与文件清晰度是不同问题。一张非常清楚的旧图仍可能不适合解释当前代码。导出图应保留版本名并与图源对应，不能只替换标题就声称反映了新的接口、字段和构造方式。

### P16. V3.1-三层架构.xmi 是否等于已经成功导入任意 UML 工具？

XMI 用于交换模型结构，目的与图片不同：图片保留展示，模型文件希望让工具理解类、关系等元素。但不同工具对格式和扩展的支持可能存在差异，文件存在并不自动证明导入效果、布局或语义完全保留。

原报告已经区分生成模型文件与实际用特定软件导入验证。答辩应沿用这种证据边界，说明实际做了哪些步骤。如果要声称某工具可用，应记录真实导入和检查结果，而不是根据扩展名推断。

### P17. 为什么 Git 提交号比“这是最新版本”更能支持答辩？

“最新”会随着继续开发而变化，提交号能定位一份确定的仓库状态。当前 Service 抽象源码提交是 `21fe14c`，随后 `327ad26` 增加对应实验报告。用这些记录可以检查当时到底修改了哪些文件，而不依赖模糊的时间描述。

仍要注意工作区可以有未提交内容，因此一个提交号不能自动代表眼前所有文件。展示时应同时说明源码版本和工作区状态，确保没有把其他用户报告改动或旧数据混入验证。提交不是测试，测试也不会自动创建提交；两者分别提供版本定位和行为证据。

## 复习时的环境核对清单

1. 说明当前源码版本及是否存在未提交源码改动。
2. 核对实际 javac/java 路径与版本，不只读取 IDE 设置。
3. 说明运行工作目录，确定访问的是哪一组数据文件。
4. 对每张图、每份报告标明版本，不把历史结构当成当前结构。
5. 将真实结果、人工推演和未来建议分开描述。

这些步骤属于可复现的工程说明，不是额外的业务功能。
